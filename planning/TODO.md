- [x] **Domain-aware fetch dispatch** — the flat `asyncio.Queue` in `_run_fetch_workers` is now `_DomainQueue` (`pka/ingestion/fetcher.py`): items are bucketed by `_throttle_key(url)` and buckets ordered on a heap by the domain's next slot, so `get()` hands back a domain that can be sent to *now*, else slot-free work, else the soonest-ready domain plus the delay to sleep first. `get()` is synchronous — choosing a bucket and claiming its slot happen with no `await` between them, which is what stops two workers reading the same domain as ready; a peek-then-claim split reopens that race. `SlotScheduler` gained `now()` / `next_slot(key)` (reserve nothing, return an **absolute** time so readings taken at different moments stay comparable) and `AsyncRateLimiter` exposes its `scheduler`, so the queue claims on the same scheduler the fetch would have. `_fetch_one` / `_fetch_one_impl` take `slot_held`, making the existing `_limiter.wait(url)` conditional — no double claim, and no claim skipped either: `_throttle_key` returns `None` for everything that does not reach the plain GET (local paths, skipped extensions, and every per-site handler, which claim their own hosts), and those items still claim inside the fetch. Side effect worth having: the rate-limit wait moved outside `_fetch_one`'s `asyncio.wait_for`, so a backed-up domain no longer eats a healthy site's per-URL budget into a spurious timeout (`_fetch_budget_seconds`'s docstring corrected). Still not solved, and said so in the class docstring: a batch made up entirely of one per-site handler's URLs carries no throttle key at all and converges on that handler's own limiter. Plan in `archive/FETCH_DISPATCH_PLAN.md`; `docs/ingestion-flows.md` redrawn (it also still named an `asyncio.Queue + Semaphore` that had not existed for a while).

## Search / vectors

- [ ] **Multilingual chunking** *(priority 1)* — `pka/ingestion/chunker.py` is English-only on both of its paths. `_SIMPLE_SENT_RE` requires an ASCII `[A-Z]` after `.!?`, so a sentence opening on `É`, `Ü` or `¿` is not a boundary; the spaCy path loads `en_core_web_sm` and falls back to `spacy.blank("en")`; and a script with neither `.!?` nor spaces (CJK, Thai) yields no boundary at all. When `_split_sentences` returns a single element, `sentence_window_chunks` emits the **whole document as one chunk**, which is then embedded as one vector — a silent retrieval failure, not a degradation. Needs language/script detection plus a per-language splitter (or a character-window fallback for unsegmented scripts); `trim_to_sentences` moves with it, since its docstring promises the same boundaries. Pairs with the embedding swap below — a multilingual model over document-sized chunks buys little, and an English-only model over correctly split non-English text buys little either.
- [ ] **Evaluate a different text embedding model** *(priority 2)* — Chroma's `DefaultEmbeddingFunction` (`all-MiniLM-L6-v2`) is used as-is in `pka/storage/vector_store.py`; benchmark retrieval quality against something like `bge-small-en-v1.5` or `gte-small` before committing, since swapping models forces a full reindex via `rebuild_from_chunks` (Chroma collections are dimension-locked). Prefer a **multilingual** candidate (`bge-m3`, `multilingual-e5-small`, `paraphrase-multilingual-MiniLM-L12-v2`) so the swap also settles the model half of the chunking item above. Sequence it after full-text retention if possible: the reindex is the expensive step and only `document_texts` makes it a *re-chunk* rather than a re-window of the chunks the old model's context size produced.
- [ ] **Full-text search over body text** *(priority 4)* — despite the name, `mode="fulltext"` in `pka/api/routers/search.py` matches `documents.title` with `ILIKE` and nothing else, so there is no keyword index over the corpus anywhere; grepping `chunks.text` is currently the only way to answer "which document contains this exact string", which is precisely what semantic search is worst at. Add an FTS5 index — over `document_texts` once priority 1 lands, see `FULL_TEXT_RETENTION.md` §11 — and point `fulltext`/`hybrid` at it, so the keyword path complements the vector path instead of silently degrading to a title match. - [x] **`upsert_chunks` doesn't batch under Chroma's max batch size** — `pka/storage/vector_store.py` passed the whole chunk list straight to `collection.upsert()`; a large document (seen: 14584 chunks from a Firefox fetch) blew past Chroma's `max_batch_size` (5461) and raised `chromadb.errors.InternalError`, so the whole doc's embedding failed (`embed_fetched_text` in `runners/firefox.py:109`) and was left with zero chunks.
